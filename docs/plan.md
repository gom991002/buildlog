# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. **서버(FastAPI)에서도 사용 권한을 검사합니다.** 화면(React)은 누구나 고쳐서 요청을 보낼 수 있기 때문입니다.
- 입력값 검사(글자 수, 공백 처리 등)는 화면과 서버 양쪽에서 하되, 최종 판단은 서버가 합니다.
- 비밀번호와 비밀 설정값(Supabase 접속 정보 등)을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, `node_modules`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- 꼭 필요하지 않은 외부 패키지는 추가하지 않습니다. 추가할 때는 이유를 기록합니다.
- 개발과 자동 테스트는 SQLite로 하고, 실제 서비스 데이터베이스인 Supabase(PostgreSQL)에서 같은 결과가 나오는지 별도 Phase에서 확인합니다.

## 3. 기술 구성

| 구분 | 기술 | 역할 |
| --- | --- | --- |
| 화면 | React (Vite로 프로젝트 생성) | 화면 표시, 서버에 데이터 요청 |
| 서버 | Python, FastAPI | 회원·기록·댓글·좋아요·신고 처리, 권한 검사 |
| 데이터 구조와 변경 이력 | SQLAlchemy, Alembic | 같은 코드로 SQLite와 PostgreSQL을 모두 다루고, 테이블 변경 이력을 관리 |
| 데이터베이스 (개발·테스트) | SQLite | 내 컴퓨터에서 바로 실행 |
| 데이터베이스 (실제 서비스) | Supabase (PostgreSQL) | 실제 사용자 데이터 보관 |
| 서버 자동 테스트 | pytest | 서버 기능 자동 확인 |

정확한 패키지와 버전은 Phase 0에서 확인해 정하고 `docs/setup.md`에 기록합니다.

## 4. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/                 # FastAPI 서버
│  ├─ requirements.txt
│  ├─ alembic.ini
│  ├─ alembic/              # 데이터베이스 변경 이력
│  ├─ app/
│  │  ├─ main.py            # 서버 시작점
│  │  ├─ core/              # 설정(.env 읽기), 비밀번호·로그인 처리
│  │  ├─ db/                # 데이터베이스 연결
│  │  ├─ models/            # 테이블 구조 (사용자, 기록, 댓글, 좋아요, 신고)
│  │  ├─ schemas/           # 주고받는 데이터 형식과 입력값 검사
│  │  ├─ routers/           # 기능별 요청 주소 (auth, studies, todos, errors, public, comments, likes, reports)
│  │  └─ services/          # 권한 검사 등 공통 규칙
│  └─ tests/                # 서버 자동 테스트
├─ frontend/                # React 화면
│  ├─ package.json
│  └─ src/
│     ├─ api/               # 서버 요청 모음
│     ├─ pages/             # 화면 (회원가입, 로그인, 기록 목록 등)
│     ├─ components/        # 공통 부품 (메뉴, 카드, 입력칸, 확인창)
│     └─ styles/            # 공통 디자인
├─ database/
│  └─ buildlog.sqlite3      # 개발용 데이터 파일, Git 제외
├─ .env.example             # 필요한 설정 항목 이름만 기록
└─ docs/                    # 요구사항, 동작 설명서, 개발 문서
```

## 7. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위가 서로 맞는지 확인하고, 5장의 확인-A~H를 정합니다. (완료)
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 사용할 Python, FastAPI, SQLAlchemy, Alembic, Node.js, React의 서로 호환되는 안정 버전을 확인합니다.
4. 비밀번호를 안전하게 저장하는 방법(비밀번호 해시 라이브러리)과 로그인 유지 방법을 정합니다. 현재 유지보수되고 있는 라이브러리인지 확인합니다.
5. SQLite가 Python 환경에서 사용 가능한지 확인합니다.
6. 서버 주소, 화면 주소, 데이터베이스 파일 위치, 환경 변수 이름을 정리합니다.
7. 테스트 명령과 서버·화면 실행 명령을 기록할 준비를 합니다.

### Phase 1. 서버·화면 뼈대와 연결

#### 목표

기능 없이도 FastAPI 서버와 React 화면이 각각 실행되고, 화면이 서버에 요청해 응답을 받아 보여줄 수 있게 합니다.

#### 작업

1. `backend/.venv`에 Python 가상환경을 만들고 FastAPI와 실행 도구만 먼저 설치합니다. 정확한 버전을 `backend/requirements.txt`에 기록합니다.
2. `backend/app/main.py`에 서버 상태 확인용 주소 하나(예: "서버가 동작 중")만 만듭니다.
3. 설정값은 `.env`에서 읽도록 하고 `.env.example`에는 항목 이름만 기록합니다.
4. `frontend/`에 Vite로 React 프로젝트를 만듭니다.
5. 화면 개발 중 서버 요청이 같은 주소로 전달되도록 개발용 연결(프록시)을 설정합니다. 이렇게 하면 화면과 서버의 주소가 달라서 생기는 접속 차단 문제(CORS)와 로그인 유지 문제를 줄일 수 있습니다.
6. React 첫 화면에서 서버 상태 확인 주소를 호출해 결과를 보여줍니다.
7. SQLite 파일(`*.sqlite3`)과 개발 중 생성되는 파일을 `.gitignore`에 보완합니다.
8. 이 Phase에서는 아직 데이터베이스를 만들지 않습니다.

#### 진행 결과 (2026-10-26)

- 서버: `backend/.venv`에 fastapi 0.162.0, uvicorn 0.54.0, pydantic-settings 2.16.1 설치. `GET /api/health` 응답 확인, `/docs` 열림 확인.
- 화면: create-vite 9.3.1의 React(JavaScript) 템플릿으로 생성. react 19.3.1, vite 8.3.5, @vitejs/plugin-react 6.1.2로 고정. 템플릿 예시 이미지는 삭제.
- 연결: Vite 프록시로 `http://localhost:5173/api/health` → 서버 응답 확인. `npm run build`, `npm run lint` 통과.
- 설정: `.env.example` 작성, `.env`에 `SECRET_KEY` 생성(값은 출력하지 않음). `.gitignore`에 `*.sqlite3`, `.pytest_cache/` 추가 후 임시 저장소에서 제외 규칙 확인.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/app/main.py`
- `backend/app/core/config.py`
- `frontend/package.json`
- `frontend/vite.config.*`
- `frontend/src/` 기본 화면
- `.env.example`
- `.gitignore`

#### 확인 방법

- 서버가 오류 없이 시작되고 상태 확인 주소가 응답하는지 확인합니다.
- FastAPI가 자동으로 만들어 주는 요청 목록 화면(`/docs`)이 열리는지 확인합니다.
- React 화면이 열리고, 서버에서 받은 상태 메시지가 화면에 보이는지 확인합니다.
- 비밀 설정값과 SQLite 파일이 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 서버와 화면이 각각 정상 실행되고 서로 통신해야 합니다.

### Phase 2. 데이터베이스 연결과 사용자 테이블

#### 목표

데이터베이스 연결 방식을 만들고, 이메일로 로그인하는 사용자 구조를 가장 먼저 확정합니다.

#### 작업

1. SQLAlchemy로 데이터베이스 연결을 만듭니다. 연결 주소는 `.env`에서 읽어, 같은 코드로 SQLite와 Supabase를 바꿔 쓸 수 있게 합니다.
2. Alembic으로 데이터베이스 변경 이력 관리를 시작합니다.
3. 사용자 테이블을 만듭니다. 회원 관리는 FastAPI가 직접 하므로 Supabase Auth를 쓰지 않습니다 (확인-F).
   - 이메일: 필수, 중복 불가. 대소문자를 구분해 입력한 그대로 비교합니다 (2026-10-26 결정).
   - 비밀번호: 원문이 아닌 안전하게 변환한 값(해시)만 저장
   - 닉네임: 필수, 2~20자, 한글·영문·숫자·밑줄만. 중복은 대소문자를 구분하지 않고 판단하며(2026-10-26 결정), 화면에는 입력한 그대로 보여줍니다. 데이터베이스에서도 소문자로 바꾼 닉네임 기준으로 중복을 막아, 동시에 가입해도 중복이 생기지 않게 합니다.
   - 가입 날짜와 시간
4. 날짜와 시간은 세계 표준시(UTC)로 저장하고, 화면에서 한국 시간으로 보여주는 방식으로 정합니다. SQLite와 PostgreSQL의 시간 처리 차이를 줄이기 위해서입니다.
5. 첫 변경 이력을 만들고 `database/buildlog.sqlite3`에 적용합니다.
6. 테스트는 매번 새로 만든 테스트용 데이터베이스에서 실행되도록 준비합니다. 개발용 데이터가 테스트 때문에 지워지지 않게 하기 위해서입니다.
7. 사용자 테이블 테스트를 작성합니다.

#### 진행 결과 (2026-10-26)

### Phase 3. 회원가입·로그인·닉네임 변경

#### 목표

#### 작업

**서버 (FastAPI)**

1. 회원가입 요청을 만듭니다: 이메일·닉네임 앞뒤 공백 제거, 이메일 형식, 중복 이메일, 비밀번호 8~64자, 닉네임 조건 검사.

3. 로그아웃 요청을 만듭니다 (확인-B).
4. 현재 로그인한 사용자 정보를 돌려주는 요청을 만듭니다.
5. 닉네임 변경 요청을 만듭니다. 본인 닉네임만 바꿀 수 있습니다.
6. 로그인이 필요한 요청에 로그인하지 않고 접근하면 거부하는 공통 검사를 만듭니다.

**화면 (React)**

7. 회원가입 화면: 실패 시 이유를 보여주고 이메일·닉네임은 유지, 비밀번호만 지웁니다. 성공하면 로그인 화면으로 이동합니다.
8. 로그인 화면: 실패 시 이메일은 유지, 비밀번호만 지웁니다. 성공하면 내 기록 홈 화면으로 이동합니다.
9. 내 기록 홈 화면의 빈 틀을 만듭니다 (카드 내용은 기록 기능이 생긴 뒤 Phase 12에서 채움).
10. 로그아웃하면 로그인 화면으로 이동합니다.
11. 계정 설정 화면: 닉네임 변경, 실패 시 입력한 닉네임 유지.
12. 로그인하지 않은 상태로 기록 화면에 들어가면 로그인 화면으로 보냅니다.
13. 위쪽 메뉴의 기본 틀을 만듭니다 (로그아웃 버튼 포함).

8. 데이터 구조와 상태 변경 테스트를 작성합니다.

### Phase 13. Supabase 연결과 PostgreSQL 검증

#### 목표

개발 중 SQLite로 만든 기능이 실제 서비스 데이터베이스인 Supabase(PostgreSQL)에서도 똑같이 동작하는지 확인합니다.

#### 작업

1. Supabase 프로젝트의 접속 정보를 `.env`에만 저장합니다. 코드나 문서에는 적지 않습니다.
2. 같은 변경 이력(Alembic)을 Supabase 데이터베이스에 적용합니다.
3. **Supabase의 자동 데이터 접근 기능을 막습니다.** Supabase는 기본 설정에서 테이블을 인터넷 요청으로 바로 읽고 쓸 수 있는 통로(Data API)를 열어둘 수 있습니다. BuildLog는 모든 요청을 FastAPI가 처리하므로, 이 통로로는 어떤 테이블도 읽거나 쓸 수 없게 설정합니다 (예: 모든 테이블에 Row Level Security를 켜고 허용 규칙을 두지 않음). 설정 방법은 이 Phase에서 Supabase 공식 문서로 확인합니다.
4. 서버 자동 테스트 전체를 Supabase용 테스트 데이터베이스(실제 서비스 데이터와 분리)에서 실행합니다.
5. SQLite와 결과가 다른 부분(검색 대소문자, 날짜·시간, 정렬, 글자 수 등)을 찾아 고칩니다.
6. 고친 뒤 SQLite에서도 다시 테스트해 양쪽 모두 통과하는지 확인합니다.

#### 예상 변경 파일

- `.env.example` (항목 이름만)
- `backend/app/db/`
- 차이가 발견된 기능의 서버 코드와 테스트
- `docs/setup.md`

#### 확인 방법

- 같은 자동 테스트가 SQLite와 Supabase 양쪽에서 모두 통과하는지 확인합니다.
- Supabase의 자동 데이터 접근 통로로 테이블을 읽을 수 없는지 확인합니다.
- 접속 정보가 Git 기록 대상에 없는지 확인합니다.

#### 완료 조건

- 양쪽 데이터베이스에서 전체 자동 테스트가 통과해야 합니다.

- [ ] 할 일을 만들고 완료·취소·필터·수정·삭제할 수 있습니다.
- [ ] 오류를 만들고 검색·해결·미해결 전환·수정·삭제할 수 있습니다.
- [ ] 모든 새 기록은 기본 비공개입니다.
- [ ] 비공개 기록은 작성자 외 사용자에게 노출되지 않습니다.
- [ ] 공개 기록 세 종류의 필터와 검색이 동작합니다.

- [ ] 신고 중복이 방지되고 운영자만 신고 내용을 봅니다.

#### 완료 조건

- 모든 자동 테스트와 최종 확인표가 통과해야 합니다.
- 설치 및 실행 문서만 보고 다른 사람이 서비스를 실행할 수 있어야 합니다.

## 8. 실제 진행 방법

1. 첫 작업은 Phase 0만 진행합니다.
2. Phase 0의 결과와 확인 내용을 공유합니다.
3. 사용자가 확인하면 Phase 1만 진행합니다.
4. 이후에도 같은 방식으로 Phase 하나씩 진행합니다.
5. 여러 Phase를 한 번에 구현하지 않습니다.
